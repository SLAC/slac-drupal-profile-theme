## The `@swc/core` version

Installed first at upstream 5.3.2's tested resolutions (`@swc/core` 1.4.11, `swc-loader` 0.2.6, `core-js` 3.36.1). The build passed, but `dist/js` grew **277,909 → 365,945 bytes (+32%)**: no arrow functions or `const` left, core-js polyfills injected everywhere (`transitions.es6.js` 2.2K → 11.7K, `filter-modal.es6.js` 2.2K → 24.6K), and `libcheck` newly reported `alert_bar` waiting on the common chunk.

Cause: SWC 1.4.11 does not read the `browserslist` key in `package.json`; asked directly (`debug: true`) it reports every target as `None`, so it lowers to ES5 in loose mode and polyfills for it. Bisected against a scratch install with our browserslist: **1.4.11, 1.4.17, 1.5.0, 1.5.25, 1.7.6, 1.11.13, 1.11.15, 1.11.16, 1.11.18 ignore it; 1.11.20, 1.11.21 … 1.13.3 … 1.16.2 read it.** (Upstream's own lockfile has 1.4.11 → 1.5.25 → 1.7.6 → 1.11.13 through 5.4.2 and 1.13.3 from 5.4.3, so upstream shipped ES5 builds for those releases.)

Loose-mode ES5 lowering is not provably inert (spread and `for…of` over NodeLists/iterables change meaning), so that is stop condition 2 unless avoided. **Taken instead: `@swc/core` 1.11.20**, the lowest version that honours the targets; `package.json` keeps upstream's `^1.4.6`. W6-D9's float landed on 1.16.2, which also honours them. At 5.4.3 upstream's 1.13.3 passes us and the pin rejoins upstream.
